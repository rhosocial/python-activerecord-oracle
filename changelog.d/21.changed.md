Split the single `IntrospectionSupport` protocol into core's four families — `StructureIntrospectionSupport`, `OperationalStatsIntrospectionSupport`, `DataProfileIntrospectionSupport` and `DdlExtractionIntrospectionSupport`, each with an async twin — and classify Oracle's capabilities per family rather than as one aggregate. `Structure` and `DataProfile` are claimed, with their declined probes (`supports_extensions`, `supports_join_coverage`) recorded individually; `OperationalStats` and `DdlExtraction` are refused as families, since every probe answers `False` and every formatter raises by name — a family is claimed only when at least one probe answers `True`, and `isinstance` is never the classifier because core's composition keeps every member reachable. The info panel groups the probes per family instead of printing one Introspection row, and `supports_partition_info` gives way to `supports_partition_metadata_introspection`, which the CLI's `partitions` type actually reads. The introspectors also answer core's neutral object-state API — `get_table_state`, `get_partition_state`, `list_index_states`, `list_constraint_states`, `list_sequence_states`, `list_schemas`, `list_derived_objects` and `item_exists` — with core's state records rather than Oracle-specific ones. An unpartitioned table answers an empty `PartitionState` whose `scheme` is `None`: `get_partition_state()` always returns a state record and `get_table_state().partitioning` is always filled, so no caller has to test for a bare `None`.
